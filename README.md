# Screen Tracker（屏幕活动分析器）

Electron 桌面截屏追踪器：定时截取主屏幕，交给本地 Ollama 视觉模型分析你当前在做什么，
把结果保存成结构化日志，并提供回顾、汇总、日记、看板与检索。**所有数据都留在本机。**

## 它是怎么工作的

```
截屏 → 本地视觉模型分析 → 结构化日志 → 10 分钟汇总 / 每日日记 / 数据看板 / 搜索问答
```

推理全部在本地 Ollama 上完成，不联网、不上传任何内容。

## 功能

- 定时自动截屏并生成 5 句活动描述
- 历史记录窗口：缩略图列表、完整分析、点击放大、每日总结
- 每 10 分钟自动结构化汇总（项目名 / 分类 / 所用软件 / 待办）
- 自动生成每日日记（简介 / 主要事项 / 亮点 / 待办 / 建议）
- 数据看板：分类占比、软件 Top10、项目耗时、每小时分布、每日堆叠
- 搜索问答：用自然语言检索历史记录
- 字体大小与颜色设置，分区域独立调节，含预设主题
- 系统托盘常驻，关闭窗口最小化到托盘
- 面向长期运行的内存优化（见「内存与性能」）

## 前置要求

- [Ollama](https://ollama.com/)，并已拉取一个**支持图像输入**的视觉模型（见「模型选择」）
- 运行方式二选一：
  - **免安装包**：不需要 Node.js
  - **源码运行**：Node.js 18 或更高

硬件没有硬性门槛。只要按「模型选择」的规则挑一个装得下的模型，低配机器也能跑。

## 安装与运行

### 方式一：免安装包

1. 到本仓库的 **Releases** 页面下载最新的 `ScreenTracker-*-win-x64.zip`
2. 解压到任意目录
3. 双击 `ScreenTracker.exe`

**装在哪里**：程序对安装位置没有要求。通用规则是——放在**你有写权限的目录**里即可，
例如用户目录下的任意子文件夹。不建议放在 `C:\Program Files` 这类需要管理员权限的位置，
以免后续出现权限相关的问题。路径中的空格和中文一般不影响使用。

**可以随意移动**：程序自身不存数据，数据写在系统的应用数据目录里（见「数据与隐私」），
所以换目录、换盘符都不会丢历史记录。

### 方式二：源码运行

```bash
git clone <本仓库地址>
cd <克隆下来的目录名>
npm install
npm start
```

目录放在哪里都行，上面用占位符表示——**不要照抄文档里任何人的绝对路径**。

## 模型选择

这是整个项目里最需要按机器情况决定的一件事：**模型是最大的内存 / 显存开销**，
选大了会溢出到内存，机器会变得又慢又卡。

### 第一步：量两个数

- **可用显存**：NVIDIA 用户执行 `nvidia-smi`；或用任务管理器 → 性能 → GPU → 专用 GPU 内存
- **物理内存**：任务管理器 → 性能 → 内存

### 第二步：估算模型要多少

- q4 量化的权重约占：`参数量 × 0.6 ~ 0.7 GB`（8B ≈ 5~6 GB，4B ≈ 2.5~3 GB，3B ≈ 2 GB）
- 视觉模型还要加上视觉编码器（约 1 GB）和每张图的 KV cache
- 别忘了系统已经占用的部分：桌面 + 浏览器通常已吃掉 1.5~2 GB 显存

**判断规则**：可用显存 = 总显存 − 已占用。如果模型总占用超过可用显存，
它就会被拆到内存里跑，速度骤降、内存紧张 —— 这时候应该降一档模型。

### 第三步：按档位初选

| 可用显存 | 可考虑的规模 | 说明 |
| --- | --- | --- |
| ≥ 7 GB | 7B~8B 视觉模型 | 质量最好，但基本吃满 |
| 5~6 GB | 4B 级 | 质量与开销的折中 |
| 3~4 GB | 3B 级或更小 | 优先保证能流畅运行 |
| 无独显 / 核显 | 3B 级以下 | 会走 CPU，速度慢，需留足内存 |

表里只是起点，最终以实际运行是否溢出为准。

### 怎么换

三种方式，任选其一：

1. `ollama pull <模型名>` 拉取模型
2. 编辑 `main.js` 顶部 `CONFIG.model`，改成该模型名，重启应用
3. **不改代码**：设置环境变量 `SCREEN_TRACKER_MODEL=<模型名>`，重启应用即可覆盖默认值

要求是**必须支持图像输入**的模型。纯文本模型无法工作，因为程序会发送截图。
可用的模型名以 `ollama list` 和官方模型库为准。

### 怎么确认有没有溢出

```bash
ollama ps
```

看 `PROCESSOR` 一列：显示 `100% GPU` 说明完全跑在显存里；
出现 CPU 百分比说明已经溢出到内存，建议换更小的模型。

## 配置项

在 `main.js` 顶部的 `CONFIG` 对象里修改：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `interval` | 35000 | 截屏间隔（毫秒） |
| `model` | `qwen3-vl:8b-instruct` | Ollama 模型名，必须是视觉模型；可用环境变量 `SCREEN_TRACKER_MODEL` 覆盖 |
| `ollamaHost` / `ollamaPort` | `127.0.0.1` / `11434` | Ollama 地址 |
| `ollamaImageWidth` | 800 | 发送给模型的图片最大宽度 |
| `ollamaImageQuality` | 75 | 发送给模型的 JPEG 质量 |
| `ollamaTimeout` | 120000 | 推理请求超时（毫秒） |
| `saveImageQuality` | 85 | 落盘截图的 JPEG 质量 |
| `savedImageWidth` | 1280 | 落盘截图宽度，`0` 表示保持原始尺寸 |
| `idlePauseSec` | 300 | 无操作超过该秒数自动暂停采集，`0` 关闭 |
| `skipUnchanged` | true | 画面基本未变时跳过推理 |
| `unchangedThreshold` | 4 | 画面差异阈值（0–255），越大越宽松 |
| `aggregationInterval` | 600000 | 10 分钟汇总间隔 |
| `autoStart` | true | 启动后自动开始追踪 |

## 内存与性能

本地视觉模型是这台机器上最大的内存开销（8B 级通常 6~8 GB）。
本项目做了三件事来避免它长期占着内存：

### 1. 空闲自动暂停

超过 `idlePauseSec`（默认 5 分钟）没有键盘鼠标输入，或系统锁屏 / 休眠时，暂停采集。
停止发请求后，Ollama 的 `keep_alive` 到期会自动卸载模型，把内存还回来。

> 取舍：挂机看视频这类「没有输入但屏幕一直在变」的场景也会被判定为空闲。
> 想记录它，就把 `idlePauseSec` 调大，或设为 `0` 关闭该功能。

### 2. 画面去重

把截图缩成 16×9 的亮度网格做比对，差异小于阈值就认为画面没变，跳过整次推理。

> 取舍：阈值设得太大可能漏掉细微变化；设得太小则几乎不省。
> 实测静止画面差异 < 1、真实切换窗口 > 8，所以默认取 4 作为保守分界。

### 3. 截图降采样落盘

落盘宽度默认 1280，体积约为原始分辨率的 1/3。

> 取舍：历史详情里看到的是 1280 宽的图，不再保留超高分辨率原图。
> 需要原图就把 `savedImageWidth` 设为 `0`。

**另外建议**给 Ollama 限流，避免并发推理把内存翻倍：

- `OLLAMA_NUM_PARALLEL=1`
- `OLLAMA_MAX_LOADED_MODELS=1`

## 数据与隐私

数据写在系统的应用数据目录下（和程序安装位置无关）：

| 系统 | 路径 |
| --- | --- |
| Windows | `%APPDATA%\screen-tracker\data` |
| macOS | `~/Library/Application Support/screen-tracker/data` |
| Linux | `~/.config/screen-tracker/data` |

```
data/
├── screenshots/YYYY-MM/     截图（JPEG）
├── logs/YYYY-MM/            每小时一个 JSON，逐条活动记录
└── summaries/
    ├── 10min/YYYY-MM/       每 10 分钟的结构化汇总
    ├── diary/               每日日记
    └── YYYY-MM-DD.json      每日总结
```

**隐私提醒**：截图是**整屏原图**，可能包含密码、聊天记录、网银页面等敏感内容。
程序不会上传任何数据，但请自行注意该目录的访问权限，不要把它同步到网盘或提交进 Git。
本仓库的 `.gitignore` 已排除 `data/`。

## 日志格式

```json
[
  {
    "timestamp": "2026-08-02 15:08:01",
    "timestampMs": 1759410481000,
    "imagePath": "screenshots/2026-08/20260802_150801.jpg",
    "activity": "用户正在浏览网页。",
    "analysisTimeMs": 3250
  }
]
```

画面未变而跳过的记录会带一个 `unchanged: true` 标记，其 `imagePath` 指向上一次实际保存的截图。

## 常见问题

**Ollama 未连接**

确认 Ollama 正在运行，并已 `ollama pull` 对应模型。

**分析很慢**

按顺序排查：① `ollama ps` 看是否溢出到内存 → 换更小模型；② 降低 `ollamaImageWidth`；
③ 加大 `interval` 减少频率。

**内存占用高**

① 先确认模型是否溢出显存（换小模型收益最大）；
② 确认 `idlePauseSec` 已启用，让空闲时能卸载模型；
③ 确认 `skipUnchanged` 打开，静态画面不再反复推理；
④ 给 Ollama 设 `OLLAMA_NUM_PARALLEL=1`。

**状态显示「已暂停」**

说明触发了空闲 / 锁屏自动暂停，动一下鼠标即会自动恢复。

**历史里有些记录没有独立截图**

那些时刻画面没有变化，记录复用了上一张截图，属正常行为。

**截图失败**

部分多显示器环境可能需要以管理员身份运行，或检查系统对屏幕捕获的权限设置。

## 设计取舍与思考

**为什么坚持本地模型**

隐私和零成本。代价是占用内存、依赖硬件，模型能力也弱于云端大模型。

**为什么只对接 Ollama**

直接使用 Ollama 的原生 HTTP 接口（`/api/chat`、`/api/version`），实现最简单。
代价是**换其他后端需要适配层**：LM Studio、vLLM、llama.cpp 等默认暴露的是 OpenAI 兼容接口，
字段格式与 Ollama 不同（图片字段、结构化输出参数、健康检查接口都不一样），目前不支持直接切换。

**为什么不做对外接口给其他 agent 调用**

两个原因：一是会把整屏截图交给被接入的 agent，如果对方是云端 agent，数据就离开了本机，
与「数据完全本地」的前提冲突；二是会出现多个进程同时读写同一批文件的问题
（当前落盘不是原子写，也没有锁）。目前 agent 想用这些数据，只能直接读上面的数据目录。

**关于分析结果的准确度**

单条记录是模型对截图的**推测**，不是事实。分类只认「工作 / 娱乐 / 学习 / 社交」四种，
其他一律归为「工作」，不会报错。误差还会逐级累积：记录 → 10 分钟汇总 → 日记 → 看板。
请把输出当参考，而不是当成准确的时间账单。
